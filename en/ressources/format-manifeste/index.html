Proof manifest format, field by field

Reference for the preuve.yml format — six sections, the role of each field, rejected errors and why, examples of honest and dishonest proofs.

This page is the reference for the manifest format used by the “Proof page” kit. It describes the actual behaviour of the engine (store/noyau/preuves.py), read and replayed on 22 November 2026 on this Pi. It complements the article The proof manifest, line by line (journal, 20-11-2026), which used a concrete project; here the format itself is described, independently of any project.

→ See also the verification arsenal : the commands actually run on the Pi, what each one checks and the trap it avoids.

1. Location and binding to the project

A manifest is a YAML file named preuve.yml placed in store/projets/<slug>/preuve.yml. The path binds the manifest to the project, not the projet: key: the engine never reads that key. It is declarative, for the human reading the file.

projet: kit-preuve      # declarative — not read by the engine
commandes: …

A project without a manifest is reported by contrôle() as <slug> : manifeste absent (…/preuve.yml) and the build fails.

2. The six sections

Section Shape Read by collecter() Checked by contrôle()
tests list of {fichier, commande} yes existence of fichier
commandes list of {titre, commande} yes —
compteurs list of {titre, base, sql} yes existence of base
fichiers list of paths yes existence of each path
captures list of {image, titre} or paths yes existence of image
limites list of free text yes (flattened) —

A missing section means an empty list. commandes and limites are the only sections contrôle() checks nothing about: a failing command is a proof of failure, not a build error.

3. Field by field

tests — fichier, commande

tests:
  - fichier: tests/test_verifier_site.py
    commande: python3 -m unittest tests.test_verifier_site -q
  • fichier: source containing def test_… definitions. The number of tests shown is counted by a regex on that source (r"^\s*def (test_\w+)", multiline flag), not read from the command output. Missing file → count 0, and contrôle() rejects the manifest.
  • commande: shell run with shell=True from the layer root, 60 s timeout. The verdict (OK / failure) comes from the return code, not the number of tests. Deleting a def test_ lowers the number even if the command still succeeds.

The number and the verdict are therefore two distinct measurements: one comes from the file, the other from execution.

commandes — titre, commande

commandes:
  - titre: Système et architecture, relus sur la machine
    commande: uname -srm
  • titre: free label shown on the page; if absent, the engine shows the command itself.
  • commande: see execution below. Stdout and stderr are concatenated; if the output is empty, the page shows (aucune sortie).

Writing rule (not enforced by the engine): commands run with the rights of whoever builds the site and must stay read-only.

compteurs — titre, base, sql

compteurs:
  - titre: Relevés de santé enregistrés sur le Pi
    base: data/health.db
    sql: select count(*) from samples
  • base: SQLite file. An absolute path (/…) is opened as-is; otherwise it goes through the resolution described below. The connection uses URI file:…?mode=ro: read-only, the manifest cannot write to the database it measures.
  • sql: query executed; the first row of the result is shown, its columns joined by a space. An invalid query or a missing database produces an error displayed (collecter() never raises); a missing database is additionally rejected by contrôle().

fichiers — list of paths

fichiers:
  - store/noyau/preuves.py
  - store/projets/kit-preuve/README.md

For each path the engine shows the size in bytes and the first 12 hex characters of the SHA-256. A delivered file whose fingerprint changes is visible. A missing path is marked absent on the page and rejected by contrôle().

captures — image, titre

captures:
  - image: ressources/extrait-kit-page-1.png
    titre: "Exemple de rendu : extrait figé d'une page du guide"

Two accepted forms: {image, titre}, or a plain path (- ressources/image.png, empty title). The image must exist, otherwise contrôle() rejects. Put quotes around a title containing a colon, or YAML reads it as a structure.

limites — free text

limites:
  - "Cette page ne prouve aucune qualité métier."
  - "Le compteur est un instantané, pas une garantie."

Block rendered at the bottom of the page. Real trap: a limit containing : that is not quoted is read by YAML as a dictionary; the engine flattens it (_aplatir_limite) into key : value — key : value instead of displaying JSON. Quote your limits.

Path resolution and execution

  • ressources/… and assets/… resolve from store/; all other paths resolve from the layer root (~/Documents/Athena).
  • Each command runs with cwd = layer root, timeout=60 s, shell=True. Output is truncated to its last 12 lines and last 1,200 characters: a long log can hide its beginning.
  • Verdict: 0 = OK; otherwise code de retour N; timeout → timeout après 60 s; system error → Python message. The date shown (“recalculated on”) is date.today(), never a hand-written date.

4. Rejected errors, and why

contrôle('<slug>') runs before the build via store/outils/site.py. Each entry becomes an error and the build stops:

Returned error Cause Why it is rejected
<slug> : manifeste absent (…) no preuve.yml a proof page with no source of proof makes no sense
test introuvable : <fichier> tests fichier missing the test count would be a silent 0, not a measurement
fichier introuvable : <chemin> missing path in fichiers claiming a delivered file that does not exist is a lie about the content
capture introuvable : <image> missing captures image the gallery would show a broken image
base introuvable : <base> missing compteurs base the counter could not be replayed by a reader

These five messages were read verbatim by replaying contrôle() on a temporary manifest containing those five defects (22-11-2026). Conversely, a failing command, a timeout, an invalid SQL query or a missing database in collecter() are not rejected: the error is published in the page. This is the central distinction: refuse what cannot be measured, display what was measured and failed.

Beyond the engine, site.py check (store/noyau/verifier.py) also rejects a missing translation, a broken internal link, an orphan page and an unreplaced real-data token.

5. Honest and dishonest proofs

Honest: measure, show the failure, state the limit

commandes:
  - titre: Bus I2C et SPI
    commande: ls /dev/i2c-* /dev/spidev* 2>/dev/null
limites:
  - "Le bus I2C n'a pas de module i2c-dev chargé : aucun périphérique."

Here the command exits with code de retour 2 because /dev/i2c-1 does not exist; the engine shows that code, and the limite says what the proof does not show. The reader sees both the measurement and its lack of scope. That is the kit’s contract.

Dishonest: write the number instead of measuring it

commandes:
  - titre: Nombre de tests
    commande: echo "12 tests OK"        # BAD: the number is written by hand

The page will show 12 tests OK, but nothing was executed or counted. The number is an assertion, not a proof. The manifest must delegate the number to a command or a SQL counter.

Dishonest: hide the failure

commandes:
  - titre: Bus I2C
    commande: ls /dev/i2c-* 2>/dev/null || true   # BAD: || true forces code 0

|| true turns a failure into a success: the “OK” verdict shown no longer means anything. Same effect with a redirection that hides stderr while the command fails, or a forced exit 0. An honest proof lets the real return code appear.

Dishonest: biased selection and missing limits

A manifest that measures only what flatters it — omitting failing tests, missing files or the limites section — is still technically valid for contrôle(). The engine cannot judge the honesty of the choice of measurements: that is why the manifest is public in the repository and the limites section is expected. A reader must be able to see what is measured and what is not.

6. What the format does not guarantee

  • That the chosen measurements are representative: that is a human choice, visible in the public manifest.
  • That the commands are harmless: that is a writing rule, not an engine guard.
  • That the beginning of a long output is visible: truncated to 12 lines / 1,200 characters.
  • That tests of the engine itself exist: trust currently rests on code review and the replayed examples (backlog task T89).
