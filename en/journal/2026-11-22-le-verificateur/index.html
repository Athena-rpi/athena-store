The verifier, or how the site avoids cheating

What noyau/verifier.py checks, and the test that proves it checks anything — with a real case it caught.

siteverificationtests

Its job

noyau/verifier.py is the site’s guard before publication. A single function, verifier(pages), takes every rendered page and returns a list of Probleme: a level (erreur or avis) and a message. site.py build fails if any erreur remains; an avis is printed but does not block.

It checks four things:

  1. Language parity. A slug present in French but not English (or the reverse) raises a warning: the translation is missing.
  2. Internal links resolved in the page’s language. External links, mailto:, # anchors and // URLs are ignored. A link to ressources/ or assets/ points at a file in dist/: if it is missing, that is an erreur. A content link is compared against existing slugs; if it leads nowhere, that is an avis.
  3. Published files with no source. Any file in dist/ that matches no page, resource or generated category page is reported as an avis — often a leftover from an older build.
  4. Unreplaced real-data tokens. Tokens delimited by two @ signs (USDC, BTC, DATE_VERIF…) and defined in moteur.JETONS — USDC address, BTC address, verification date, test count, measurement count and today’s date — must have been substituted by the engine. If one survives in the HTML, that is an erreur: the site would show raw text instead of a verified figure.

The test that proves it works

tests/test_verifier_site.py holds 11 independent tests. None touches the network or the real dist/: each test redirects the three paths the verifier reads to a temporary folder, then restores them. It injects a synthetic defect and checks that the verifier reports it — and that it reports nothing on a clean site.

Verified locally:

python3 tests/test_verifier_site.py
Ran 11 tests in 0.007s
OK

In other words: break any of the four rules above and at least one test fails. The verifier protects not just publication, but its own logic against regressions.

A real case it caught

The most instructive is a false positive the verifier produced itself. On 18 November 2026 (commit 91cb7b6), the link rule compared only the last segment of the URL: for a projets/ link it kept projets and compared it to the slugs. But the page is named projets/index. Result: a perfectly valid link was flagged « lien vers « projets/ » hors contenu ».

The fix (commit 96bbe9b, a few hours later) generates several candidates, including projets/index, before concluding. The test test_lien_projets_resout_vers_index locks that behaviour in: it creates a projets/index page and requires the projets/ link to produce no problem. Without the fix, that test fails — proof that it is checking something.

The lesson: a guard that cries wolf is as dangerous as one that stays silent, because people end up ignoring its warnings. Hence the value of regression tests on the verifier itself.

Known, documented limit: the relative-root token (the ../ prefix inserted before links) is substituted by the engine but is not part of moteur.JETONS. The verifier therefore does not watch it — the test test_racine_token_non_surveille states this explicitly.
