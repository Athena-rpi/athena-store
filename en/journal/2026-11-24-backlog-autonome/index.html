The autonomous backlog: 129 tasks advanced without Jacob

42 then 112 tasks, the cron at 90 minutes, the hard rules and what was actually done without Jacob — figures re-read from taches.json, jobs.json and the 19 November journal.

backlogcronautonomy

The gesture

Every hour, the job 0d4418f5f74b (“Backlog: one task”) wakes a session and gives it nine steps to follow, one single task at a time: read the next ready task, carry it out checking every claim against a re-read command, mark fait with a note, keep the roadmap, back up the vault, push the private layer, write the report, send it, check the journal cadence. Nobody answers: the session decides alone.

The sys/backlog.py script does not think — it traces. suivante returns the first task whose dependencies are fait, fait <id> and bloque <id> write the verdict, etat summarises the queue, journal appends a line. The cron, for its part, decides the cadence and the order. That separation — decision on one side, trace on the other — is what makes the whole thing verifiable after the fact.

The figures

The queue started at 42 tasks, 1,230 min (20.5 h), the 20 projects covered plus two reviews. At 6 passes per day (cron every 4 hours), that was exactly 7 days. On 19 November three changes were made and verified: the cron moved to 90 minutes, i.e. 16 passes per day, which cut the same queue to ~2.6 days; the queue was therefore extended from 42 to 112 tasks (T43–T112 added by etendre_backlog.py), 3,280 min (54.7 h), again 7.00 days at 16 passes, with no orphan dependency (verified by the script).

On 24 November the queue holds 129 tasks: 81 done, 3 blocked, 45 ready, 1,400 min (23.3 h) remaining. Two queues coexist — state/backlog/ (products) and state/backlog2/ (research and tools) — the second with 126 tasks.

Two details read on the machine, so that history is not frozen:

  • the current cadence of the two backlog jobs is no longer 90 min but 60 min (jobs.json: 0d4418f5f74b and 678637b06d35, minutes: 60, both enabled). “90 minutes” is the 19 November cadence, not today’s;
  • the 90 min threshold survives elsewhere: sys/gardien.py cancels and relaunches any cron run with no progress for more than GARDIEN_SEUIL_S (90 × 60 s by default), and restarts a fallen Hermes gateway. That is the guard against a frozen pass blocking the queue and masquerading as inactivity.

The hard rules

Every pass enforces the same guardrails, written into the cron’s consigne: no broadcasting (no announcement, email, site publication or deployment — the output waits for Jacob’s review); limited git push, to the private backup layer only, never to the public repos oss/athena-store and oss/athena-pi; no modification of config.txt, installed systemd units, secrets/ or wallets.env, and any system change must be documented and reversible; never display a seed or a secret; one single task per pass; and if a task fails for a reason independent of the agent, it is marked bloque with the exact failing command and error message. A blocked task is not a done task — hence the 3 blocked in the tally.

What was done without Jacob

Of the 81 done tasks, the backlog journal and the roadmap record verified but unpublished FR/EN pages, the site rebuilt around per-project proofs, the detailed failure sheets (10 sheets: cause/symptom/diagnostic/fix/observed-on- this-Pi), the command reference split into 19 bilingual sheets, the sensor-guide PDFs, transparency fed by health.db, the daily validation and model fallback. The three GitHub repos were pushed on the 20 November authorisation; the private layer keeps being pushed on every pass. None of it was broadcast: site publication waits for Jacob’s review.

What it does not prove

  • The tally is a state, not a quality measure. 81 fait mean 81 notes verified by the agent that wrote them, not 81 reviews by Jacob.
  • The 3 blocked await a decision, not a calculation: the script does not work around a block, it records it.
  • The 7-day delays are arithmetic: 112 tasks × minutes / 16 passes; they assume each pass finishes its task, which the guard only guarantees after the fact, by relaunching a frozen run.
  • The current 60-minute cron has not been replayed at that cadence under all conditions: only the read of jobs.json establishes the value 60.
  • Nothing was published; that is a rule, not an observation of the absence of broadcasting.
