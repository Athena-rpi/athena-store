These ten detailed sheets take the failures of the Failure FAQ one by one. Each sheet separates five elements: the cause, the symptom, the diagnostic command, the fix, and above all how it was observed on this Pi — a command actually re-run, a value read or a cited file with its reference. Facts dated 24 November 2026 were re-verified on the day of writing; the others are historical facts whose durable trace is indicated. When the cost was not priced in money, it is given in time or risk, and that is stated.

Sheet 1 — Free-tier quota exhausted (HTTP 429)

  • Cause : the model pinned for cron jobs (qwen/qwen4-max:free) is in « fair-share »; the router replies retry after 122 s. A restart fixes nothing: the model answers, but the quota is full.
  • Symptom : the scheduler runs, the jobs are active and scheduled, but executions fail one after another. This is not a broken cron; it is an exhausted quota.
  • Diagnostic command : grep -n '429' data/gardien_message.txt — look for « fair-share 429 » and the retry delay, then compare with the model’s own answer.
  • Fix : wait for the quota to free up or pin another free model; add backoff/retry instead of restarting. The tencent/hy4-flash:free fallback is verified operational.
  • Observed on this Pi : re-run on 24-11, data/gardien_message.txt:5 carries « fair-share 429 — the router replies « retry after 122 s » » and :3 reports « backlog 1 had just failed eight times in a row ». The same file notes a restart had fixed nothing, the model having answered the check. Cost : cron paralysed until the restart (time, not money).

Sheet 2 — Frozen cron run

  • Cause : a run stays open (finished_at NULL) and keeps making progress; the queue behind it stalls. The watchdog used a 0-minute threshold, so its logged duration did not measure the real duration.
  • Symptom : « cancelled … frozen for 0 min (threshold 0 min) » in the watchdog log; no following job starts, which looks like inactivity while the queue is blocked.
  • Diagnostic command : grep -n 'annulé' logs/gardien.log — read the cancellation timestamps and the displayed threshold.
  • Fix : sys/gardien.py (15-minute timer) cancels and relaunches beyond 90 min (GARDIEN_SEUIL_S); the interrupted run stays in the queue and resumes next pass, nothing is lost.
  • Observed on this Pi : re-run on 24-11, logs/gardien.log:2 and :8 give two cancellations on 2026-11-21 at 13:07:58 and 13:08:01 EST, both « frozen for 0 min (threshold 0 min) » (jobs 0d4418f5… and 678637b0…). data/gardien_message.txt:3 reports a backlog 2 run open since 19:43, i.e. 2 h 28 lost. Cost : 2 h 28 of blocked queue.

Sheet 3 — Revenue ledger: slow, non-incremental scan

  • Cause : the scan is not incremental; it is capped at 200 000 blocks. State is written to latest even when the scan is truncated, so a transfer outside the window can be missed.
  • Symptom : the 08:50 cron takes ~20 min; manual runs at 09:00 exceed 60 s and then 300 s.
  • Diagnostic command : grep -n -i 'scan\|RPC\|blocs\|ledger' data/daily_report.txt data/auto_analyse.txt data/weekly_report.txt — do not use a fixed line number: the daily report is regenerated every day and its lines rotate (on 24-11, line 4 is a health reading, not the ledger).
  • Fix : resume from data/ledger_state.json and do not advance latest while the scan is capped; then rerun wallet/ledger.py. The 22-11 09:10 pass exited 0 with 0 transfer.
  • Observed on this Pi : on 24-11, data/daily_report.txt:2 records ledger.py exit 0, BTC 0 tx, USDC/Base 0, USDC/Ethereum 17.28, “Blocks scanned: Base 61 695 661 / ETH 26 485 536, 0 transfer” (08:50:32), and :3 flags the 08:50 pass still active at 09:00 (catching up). The historical incident is durably traced in data/auto_analyse.txt:29,38 (“scan capped at 200 000 blocks, ~2 000 RPC calls”, ~20 min) and data/weekly_report.txt:23 (latest state advanced despite the cap). Cost : ~20 min/day and risk of a missed transfer.

Sheet 4 — Failed git pushes

  • Cause : network or SSH key unavailable when the backup cron ran.
  • Symptom : « ÉCHEC de poussée (réseau ou clé SSH) » in the log; the commit stays local, the private layer is not up to date on the repository.
  • Diagnostic command : grep -n 'ÉCHEC de poussée' logs/git_sync.log | tail.
  • Fix : restore the network/key, then replay bash sys/git_sync.sh; the script re-reads @{u}..HEAD so an already-made local commit still gets pushed.
  • Observed on this Pi : re-run on 24-11, logs/git_sync.log:141 carries [2026-11-22T03:45:56-05:00] ÉCHEC de poussée and :148 [2026-11-22T06:17:25-05:00] — two failures in under 2 h 30. Cost : private layer not backed up during the incident (risk, not money).

Sheet 5 — Broken IPv6

  • Cause : dual-stack resolution waits for the IPv4 fallback before connecting.
  • Symptom : every network request blocks for ~24 s, then succeeds over IPv4.
  • Diagnostic command : grep -n 'precedence ::ffff:0:0/96' /etc/gai.conf /etc/gai.conf.bak-20261118 — compare the active line in the current file with the commented line in the backup.
  • Fix : precedence ::ffff:0:0/96 100 in /etc/gai.conf (backup .bak-20261118) → IPv4 first, ~0.02 s. Workaround: curl -4 or getaddrinfo filtered to AF_INET.
  • Observed on this Pi : re-run on 24-11, line 66 of /etc/gai.conf is active (precedence ::ffff:0:0/96 100) while lines 50 and 54 are commented in /etc/gai.conf.bak-20261118. The gain measured before the fix is recorded in HARDWARE.md:102-106. Cost : ~24 s per request before the fix (time).

Sheet 6 — Floating 1-Wire bus, ghost ROMs

  • Cause : no sensor connected and no pull-up resistor to 3V3; the bus enumerates invalid devices whose identifier changes on every search.
  • Symptom : 00-… entries appear in /sys/bus/w1/devices/; w1_master_attempts climbs; the kernel logs « Family 0 … is not registered ».
  • Diagnostic command : ls /sys/bus/w1/devices/ — read it twice: if the identifier changes, it is not a sensor.
  • Fix : a 4.7 kΩ pull-up to 3V3 on GPIO4 (+ ground) and a real DS18B20 (family 0x28). While only 00-* devices show up, no temperature reading is valid. No hardware is being bought: the project is frozen by Jacob.
  • Observed on this Pi : on 24-11, ls /sys/bus/w1/devices/ returns 00-034400000000, 00-fd4400000000, w1_bus_master1 — identifiers different from those read on 22-11 in the FAQ (00-436800000000, 00-836800000000), confirming they are ghosts. HARDWARE.md:50-54,144-147 describes the floating bus and required pull-up. Cost : false measurements and wasted diagnostic time.

Sheet 7 — /dev/i2c-1 missing at boot

  • Cause : dtparam=i2c_arm=on enables the RP1 node (i2c@74000, GPIO2/3) but the i2c-dev module is not loaded at boot.
  • Symptom : no /dev/i2c-* exists; i2cdetect fails even though the hardware node is okay.
  • Diagnostic command : ls /dev/i2c-* 2>&1; lsmod | grep i2c_dev — the first fails, the second returns nothing.
  • Fix : load the module persistently with echo i2c-dev | sudo tee /etc/modules-load.d/i2c-dev.conf (manually, outside cron). Trap: i2c-13/i2c-14, when present, are HDMI DDC — not the header.
  • Observed on this Pi : re-run on 24-11, ls /dev/i2c-* replies “No such file or directory” and lsmod | grep i2c_dev returns nothing, while HARDWARE.md:44-47 records a manual modprobe i2c-dev around 15:55 on 22-11 — the module is therefore indeed lost on every reboot. Cost : I2C bus unavailable after each restart (diagnostic time).

Sheet 8 — « GPU » inference sixteen times slower

  • Cause : the WebGPU delegate (Dawn/Vulkan) requires shaderUniformBufferArrayDynamicIndexing and shaderSampledImageArrayDynamicIndexing, which the v3dv driver (mesa 26.2.2, V3D 7.1.10.2) does not expose (= 0). Dawn rejects V3D and falls back to llvmpipe (software).
  • Symptom : 278.7 ms instead of 16.8 ms on 4-thread CPU (16.6× slower); worse, CompiledModel(ptr, env) reports « GPU OK » while loading no model at all.
  • Diagnostic command : python3 litert/probe_vulkan.py (V3D features at 0); compare with CompiledModel.from_file(...) and the measurements in data/litert_etat.txt.
  • Fix : stay on 4-thread CPU XNNPACK; never validate a model with the bare constructor. No NPU on Pi 5 (Qualcomm plugin unusable, libQnnSystem.so absent).
  • Observed on this Pi : on 24-11, litert/probe_vulkan.py is read (2 514 bytes) and data/litert_etat.txt:20-26 gives 16.80 ms at 4 threads, :44,58 give 278.7 ms on “GPU” and the verdict “16.6× slower”, :48 identifies llvmpipe (LLVM 19.1.7), :51-55 the two features at 0. HARDWARE.md:177-189 records the hardware law. Cost : ×16 inference time and false validation.

Sheet 9 — Status page 8081, Backlog panel in error

  • Cause : two bugs in health_web.py — backlog.charger() called without its fichier argument, and a reference to backlog.JOURNAL, an attribute that does not exist (the journal is state/backlog/journal.md).
  • Symptom : the local home page cannot show the upcoming actions; the Backlog panel goes into error.
  • Diagnostic command : curl -s --max-time 6 -4 http://127.0.0.1:8081/ | grep -i backlog, then python3 tests/verifier_accueil.py (12 checks).
  • Fix : pass the file path to charger() and read state/backlog/journal.md; verify with verifier_accueil.py.
  • Observed on this Pi : on 24-11, the local curl answers (code 0) and the HTML contains the backlog, /api/backlog and “backlog/taches.json · tâches prêtes dont les dépendances sont faites” markers. HARDWARE.md:294-298 records the two fixed bugs and the backlog journal T04 the return to service. Cost : monitoring page unusable until fixed.

Sheet 10 — RPi.GPIO and numbering on RP1

  • Cause : the header is driven by the RP1 southbridge (gpiochip0); RPi.GPIO does not drive it correctly, and physical pin numbers are not BCM numbers.
  • Symptom : failed gpio import or call, unresponsive pins, or the wrong GPIO targeted. Hardware risk if 5 V is applied to the header (3.3 V logic).
  • Diagnostic command : gpiodetect; gpioinfo | grep onewire — verify the controller and the line, never the pin number.
  • Fix : use lgpio or gpiod/libgpiod, reason in BCM verified via gpioinfo, never in pin numbers; 3.3 V only, series resistor on LEDs, separate driver for loads. Lines 0/1 (HAT EEPROM) and 44/45/29/42/43 (kernel) are reserved.
  • Observed on this Pi : re-run on 24-11, gpiodetect gives gpiochip0 [pinctrl-rp1] (54 lines) (plus gpiochip 10 to 13 from the SoC) and gpioinfo gives line 4: "GPIO4" output drive=open-drain consumer="onewire@0". HARDWARE.md:56-72 records the reserved lines and the 3.3 V rule. Cost : GPIO code to rewrite and risk to the board.
