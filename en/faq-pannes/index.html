Failure FAQ — the ten most costly incidents

Ten failures that really happened on this Raspberry Pi 5, with cause, symptom, diagnostic command and fix — every entry backed by a fact read on the machine.

This page lists the ten most costly incidents on this Raspberry Pi 5 — in lost time, reliability or risk. These are not hypothetical failures: every entry is backed by a file that was read or a command that was re-run on the machine, with the reference given at the end of the entry. The cost is the one that was measured or reported; when it was not priced in money, it is expressed in time or risk, and that is stated.

1. Free-tier quota exhausted (HTTP 429) — eight cron failures in a row

  • Cause : the model pinned for cron jobs (qwen/qwen4-max:free) is in « fair-share »; the router replies retry after 122 s. A restart fixes nothing: the model answers, but the quota is full.
  • Symptom : the scheduler runs and the jobs are active, but executions fail one after another. This is not a broken cron.
  • Diagnostic : grep -n '429' data/gardien_message.txt → « fair-share 429 … retry after 122 s ».
  • Fix : wait for the quota to free up or pin another free model; add backoff/retry instead of restarting.
  • Recorded fact : data/gardien_message.txt:3,5,9 — « backlog 1 had just failed eight times in a row ». Cost : cron paralysed until the restart.

2. Frozen cron run — 2 h 28 lost, queue blocked

  • Cause : a run stays open (finished_at NULL) and keeps making progress; the queue behind it stalls. The watchdog used a 0-minute threshold, so its logged duration did not measure the real duration.
  • Symptom : « cancelled … frozen for 0 min (threshold 0 min) » in the watchdog log; no following job starts, which looks like inactivity.
  • Diagnostic : grep -n 'annulé' logs/gardien.log → two cancellations on 2026-11-21 at 13:07.
  • Fix : sys/gardien.py (15-minute timer) cancels and relaunches beyond 90 min (GARDIEN_SEUIL_S); the interrupted run stays in the queue and resumes next pass, nothing is lost.
  • Recorded fact : logs/gardien.log:2,8 and data/gardien_message.txt:3 — backlog 2 run open since 19:43 (2 h 28).

3. Revenue ledger — 20 minutes per pass, ~2 000 RPC calls

  • Cause : the scan is not incremental; it is capped at 200 000 blocks. State is written to latest even when the scan is truncated, so a transfer outside the window can be missed.
  • Symptom : the 08:50 cron takes ~20 min; manual runs at 09:00 exceed 60 s and then 300 s.
  • Diagnostic : sed -n '4p' data/daily_report.txt → « scan capped at 200 000 blocks, ~2 000 RPC calls ».
  • Fix : resume from data/ledger_state.json and do not advance latest while the scan is capped; then rerun wallet/ledger.py (exit 0, 0 transfer on 22-11 at 09:10).
  • Recorded fact : data/daily_report.txt:4 — cost : 20 min/day and risk of a missed transfer.

4. Failed git pushes — delayed backup

  • Cause : network or SSH key unavailable when the backup cron ran.
  • Symptom : « ÉCHEC de poussée (réseau ou clé SSH) » in the log; the commit stays local, the private layer is not up to date on the repository.
  • Diagnostic : grep -n 'ÉCHEC de poussée' logs/git_sync.log | tail → two failures on 2026-11-22 (03:45 and 06:17).
  • Fix : restore the network/key, then replay bash sys/git_sync.sh; the script re-reads @{u}..HEAD so an already-made commit still gets pushed.
  • Recorded fact : logs/git_sync.log:141,148. Cost : private layer not backed up during the incident.

5. Broken IPv6 — 24 seconds lost per request

  • Cause : dual-stack resolution waits for the IPv4 fallback before connecting.
  • Symptom : every network request blocks for ~24 s, then succeeds over IPv4.
  • Diagnostic : grep -n 'precedence ::ffff:0:0/96' /etc/gai.conf → active line at position 66; compare with /etc/gai.conf.bak-20261118 where it is commented out.
  • Fix : precedence ::ffff:0:0/96 100 in /etc/gai.conf (backup .bak-20261118) → IPv4 first, 0.02 s. Workaround: curl -4 or getaddrinfo filtered to AF_INET.
  • Recorded fact : HARDWARE.md:102-106; the active line was re-read on the machine. Cost : ~24 s per request before the fix.

6. Floating 1-Wire bus — ghost ROMs of family 0x00

  • Cause : no sensor connected and no pull-up resistor to 3V3; the bus enumerates invalid devices whose identifier changes on every search.
  • Symptom : 00-… entries appear in /sys/bus/w1/devices/; w1_master_attempts climbs; the kernel logs « Family 0 … is not registered ».
  • Diagnostic : ls /sys/bus/w1/devices/ → read on 22-11: 00-436800000000, 00-836800000000, w1_bus_master1.
  • Fix : a 4.7 kΩ pull-up to 3V3 on GPIO4 (+ ground) and a real DS18B20 (family 0x28). While only 00-* devices show up, no temperature reading is valid.
  • Recorded fact : HARDWARE.md:50-54,144-147; bus read directly on 22-11. Cost : false measurements and wasted diagnostic time.

7. /dev/i2c-1 missing at boot — unusable bus

  • Cause : dtparam=i2c_arm=on enables the RP1 node (i2c@74000, GPIO2/3) but the i2c-dev module is not loaded at boot.
  • Symptom : no /dev/i2c-* exists; i2cdetect fails even though the hardware node is okay.
  • Diagnostic : ls /dev/i2c-* → « No such file or directory » (read on 22-11); lsmod | grep i2c_dev returns nothing.
  • Fix : load the module persistently with echo i2c-dev | sudo tee /etc/modules-load.d/i2c-dev.conf (manually, outside cron). Trap: i2c-13/i2c-14, when present, are HDMI DDC — not the header.
  • Recorded fact : HARDWARE.md:44-47,148-154 and direct read of /dev/i2c-*. Cost : I2C bus unavailable after every reboot.

8. « GPU » inference sixteen times slower — LiteRT false positive

  • Cause : the WebGPU delegate (Dawn/Vulkan) requires shaderUniformBufferArrayDynamicIndexing and shaderSampledImageArrayDynamicIndexing, which the v3dv driver does not expose (= 0). Dawn rejects V3D and falls back to llvmpipe (software).
  • Symptom : 278.7 ms instead of 16.8 ms on 4-thread CPU (16.6× slower); worse, CompiledModel(ptr, env) reports « GPU OK » while loading no model at all.
  • Diagnostic : python3 litert/probe_vulkan.py (V3D features at 0); compare with CompiledModel.from_file(...).
  • Fix : stay on 4-thread CPU XNNPACK; never validate a model with the bare constructor. There is no NPU on a Pi 5.
  • Recorded fact : HARDWARE.md:177-189; evidence data/litert_etat.txt, litert/probe_vulkan.py. Cost : ×16 inference time and false validation.

9. Status page 8081 — Backlog panel in error

  • Cause : two bugs in health_web.py — backlog.charger() called without its fichier argument, and a reference to backlog.JOURNAL, an attribute that does not exist (the journal is state/backlog/journal.md).
  • Symptom : the local home page cannot show the upcoming actions; the Backlog panel goes into error.
  • Diagnostic : curl -s http://127.0.0.1:8081/ | grep -i backlog, then python3 tests/verifier_accueil.py (12 checks).
  • Fix : pass the file path to charger() and read state/backlog/journal.md; verify with verifier_accueil.py.
  • Recorded fact : HARDWARE.md:294-298 and backlog journal T04. Cost : monitoring page unusable until fixed.

10. RPi.GPIO and numbering — unusable GPIO code on RP1

  • Cause : the header is driven by the RP1 southbridge (gpiochip0); RPi.GPIO does not drive it correctly, and physical pin numbers are not BCM numbers.
  • Symptom : failed gpio import or call, unresponsive pins, or the wrong GPIO targeted. Hardware risk if 5 V is applied to the header (3.3 V logic).
  • Diagnostic : gpiodetect → gpiochip0 [pinctrl-rp1] (54 lines); gpioinfo | grep onewire → line 4 consumer="onewire@0".
  • Fix : use lgpio or gpiod/libgpiod, reason in BCM verified via gpioinfo, never in pin numbers; 3.3 V only, series resistor on LEDs, separate driver for loads. Lines 0/1 (HAT EEPROM) and 44/45/29/42/43 (kernel) are reserved.
  • Recorded fact : HARDWARE.md:56-72; gpiodetect and gpioinfo re-read on 22-11. Cost : GPIO code to rewrite and risk to the board.
