FAQ des pannes — les dix incidents les plus coûteux

Dix pannes réellement survenues sur ce Raspberry Pi 5, avec cause, symptôme, commande de diagnostic et correctif — chaque entrée appuyée sur un fait relevé sur la machine.

Cette page recense les dix incidents qui ont coûté le plus cher sur ce Raspberry Pi 5 — en temps perdu, en fiabilité ou en risque. Ce ne sont pas des pannes hypothétiques : chaque entrée est appuyée sur un fichier lu ou une commande relue sur la machine, dont la référence figure en fin d’entrée. Le coût est celui qui a été mesuré ou relaté ; quand il n’a pas été chiffré en argent, il est exprimé en temps ou en risque, et cela est dit.

Retour à la FAQ · Les fiches détaillées ajoutent, pour chaque panne, la constatation précise relevée sur ce Pi · Voir aussi l’arsenal de vérification.

1. Quota gratuit saturé (HTTP 429) — huit échecs de cron de suite

  • Cause : le modèle épinglé pour les cron (qwen/qwen4-max:free) est en « fair-share » ; le routeur répond retry after 122 s. Un redémarrage ne répare rien : le modèle répond, mais le quota est plein.
  • Symptôme : le planificateur tourne et les jobs sont actifs, mais les exécutions échouent les unes après les autres. Ce n’est pas un cron cassé.
  • Diagnostic : grep -n '429' data/gardien_message.txt → « fair-share 429 … retry after 122 s ».
  • Correctif : attendre la libération du quota ou épingler un autre modèle gratuit ; prévoir un recul/réessai plutôt qu’un redémarrage.
  • Fait relevé : data/gardien_message.txt:3,5,9 — « le backlog 1, lui, venait d’échouer 8 fois de suite ». Coût : cron paralysé jusqu’à la relance.

2. Exécution de cron figée — 2 h 28 perdues, file bloquée

  • Cause : un run reste ouvert (finished_at à NULL) et continue de progresser ; la file derrière lui s’immobilise. Le gardien utilisait un seuil de 0 minute, donc sa durée journalisée ne mesurait pas la durée réelle.
  • Symptôme : « annulé … figé depuis 0 min (seuil 0 min) » dans le journal ; aucun job suivant ne démarre, ce qui ressemble à de l’inactivité.
  • Diagnostic : grep -n 'annulé' logs/gardien.log → deux annulations le 2026-11-21 à 13:07.
  • Correctif : sys/gardien.py (timer 15 min) annule et relance au-delà de 90 min (GARDIEN_SEUIL_S) ; le run interrompu reste dans la file et repart au passage suivant, rien n’est perdu.
  • Fait relevé : logs/gardien.log:2,8 et data/gardien_message.txt:3 — run du backlog 2 ouvert depuis 19h43 (2 h 28).

3. Grand livre — 20 minutes par passage, ~2 000 appels RPC

  • Cause : le scan n’est pas incrémental ; il est plafonné à 200 000 blocs. L’état est écrit à latest même quand le scan est tronqué, donc un transfert hors fenêtre peut être manqué.
  • Symptôme : le cron 08:50 met ~20 min ; les lancements manuels de 09:00 dépassent 60 s puis 300 s.
  • Diagnostic : sed -n '4p' data/daily_report.txt → « scan plafonné à 200 000 blocs, ~2 000 appels RPC ».
  • Correctif : reprendre depuis data/ledger_state.json et ne pas avancer latest tant que le scan est plafonné ; relancer ensuite wallet/ledger.py (exit 0, 0 transfert le 22-11 à 09:10).
  • Fait relevé : data/daily_report.txt:4 — coût : 20 min/jour et risque de transfert manqué.

4. Poussées git en échec — sauvegarde différée

  • Cause : réseau ou clé SSH indisponible au moment du cron de sauvegarde.
  • Symptôme : « ÉCHEC de poussée (réseau ou clé SSH) » dans le journal ; le commit reste local, la couche n’est pas à jour sur le dépôt privé.
  • Diagnostic : grep -n 'ÉCHEC de poussée' logs/git_sync.log | tail → deux échecs le 2026-11-22 (03:45 et 06:17).
  • Correctif : rétablir le réseau/la clé puis rejouer bash sys/git_sync.sh ; le script relit @{u}..HEAD pour pousser un commit même déjà présent.
  • Fait relevé : logs/git_sync.log:141,148. Coût : couche privée non sauvegardée pendant l’incident.

5. IPv6 cassé — 24 secondes perdues par requête

  • Cause : la résolution dual-stack attend le repli IPv4 avant de se connecter.
  • Symptôme : toute requête réseau bloque ~24 s, puis aboutit en IPv4.
  • Diagnostic : grep -n 'precedence ::ffff:0:0/96' /etc/gai.conf → ligne active en position 66 ; comparer avec /etc/gai.conf.bak-20261118 où elle est commentée.
  • Correctif : precedence ::ffff:0:0/96 100 dans /etc/gai.conf (sauvegarde .bak-20261118) → IPv4 en premier, 0,02 s. En dépannage : curl -4 ou getaddrinfo filtré sur AF_INET.
  • Fait relevé : HARDWARE.md:102-106 ; la ligne active est relue sur la machine. Coût : ~24 s par requête avant correction.

6. Bus 1-Wire flottant — ROMs fantômes de famille 0x00

  • Cause : aucune sonde branchée et aucune résistance de pull-up vers 3V3 ; le bus énumère des devices invalides dont l’identifiant change à chaque recherche.
  • Symptôme : 00-… apparaissent dans /sys/bus/w1/devices/ ; w1_master_attempts grimpe ; le noyau journalise « Family 0 … is not registered ».
  • Diagnostic : ls /sys/bus/w1/devices/ → relevé : 00-436800000000, 00-836800000000, w1_bus_master1.
  • Correctif : résistance de 4,7 kΩ vers 3V3 sur GPIO4 (+ masse) et un vrai DS18B20 (famille 0x28). Tant qu’il n’y a que des 00-*, aucune température n’est valide.
  • Fait relevé : HARDWARE.md:50-54,144-147 ; lecture directe du bus le 22-11. Coût : mesures fausses et temps de diagnostic perdu.

7. /dev/i2c-1 absent au boot — bus inutilisable

  • Cause : dtparam=i2c_arm=on active le nœud RP1 (i2c@74000, GPIO2/3) mais le module i2c-dev n’est pas chargé au démarrage.
  • Symptôme : aucun /dev/i2c-* n’existe ; i2cdetect échoue, alors même que le nœud matériel est okay.
  • Diagnostic : ls /dev/i2c-* → « No such file or directory » (relevé le 22-11) ; lsmod | grep i2c_dev ne renvoie rien.
  • Correctif : charger le module de façon persistante avec echo i2c-dev | sudo tee /etc/modules-load.d/i2c-dev.conf (à faire à la main, hors cron). Piège : i2c-13/i2c-14, quand ils existent, sont le DDC HDMI — pas le header.
  • Fait relevé : HARDWARE.md:44-47,148-154 et lecture directe des /dev/i2c-*. Coût : bus I2C indisponible après chaque reboot.

8. Inférence « GPU » seize fois plus lente — faux positif LiteRT

  • Cause : le delegate WebGPU (Dawn/Vulkan) exige shaderUniformBufferArrayDynamicIndexing et shaderSampledImageArrayDynamicIndexing, que le pilote v3dv n’expose pas (= 0). Dawn rejette V3D et retombe sur llvmpipe (logiciel).
  • Symptôme : 278,7 ms au lieu de 16,8 ms en CPU 4 threads (16,6× plus lent) ; pire, CompiledModel(ptr, env) affiche un « GPU OK » alors qu’il ne charge aucun modèle.
  • Diagnostic : python3 litert/probe_vulkan.py (features V3D à 0) ; comparer avec CompiledModel.from_file(...).
  • Correctif : rester en CPU XNNPACK 4 threads ; ne jamais valider un modèle avec le simple constructeur. Pas de NPU sur Pi 5.
  • Fait relevé : HARDWARE.md:177-189 ; preuves data/litert_etat.txt, litert/probe_vulkan.py. Coût : temps d’inférence ×16 et fausse validation.

9. Page de statut 8081 — panneau Backlog en erreur

  • Cause : deux bugs dans health_web.py — backlog.charger() appelé sans son argument fichier, et référence à backlog.JOURNAL, attribut inexistant (le journal est state/backlog/journal.md).
  • Symptôme : la page d’accueil locale ne peut pas afficher les prochains actes ; le panneau Backlog part en erreur.
  • Diagnostic : curl -s http://127.0.0.1:8081/ | grep -i backlog puis python3 tests/verifier_accueil.py (12 contrôles).
  • Correctif : passer le chemin du fichier à charger() et lire state/backlog/journal.md ; vérifier avec verifier_accueil.py.
  • Fait relevé : HARDWARE.md:294-298 et journal backlog T04. Coût : page de surveillance inutilisable jusqu’au correctif.

10. RPi.GPIO et numérotation — code GPIO inopérant sur RP1

  • Cause : le header est piloté par la southbridge RP1 (gpiochip0) ; RPi.GPIO ne le pilote pas correctement, et la numérotation physique n’est pas la numérotation BCM.
  • Symptôme : import ou appel gpio défaillant, broches qui ne répondent pas, ou mauvais GPIO ciblé. Risque matériel si 5 V est appliqué au header (logique 3,3 V).
  • Diagnostic : gpiodetect → gpiochip0 [pinctrl-rp1] (54 lines) ; gpioinfo | grep onewire → ligne 4 consumer="onewire@0".
  • Correctif : utiliser lgpio ou gpiod/libgpiod, raisonner en BCM vérifié par gpioinfo, jamais en numéro de broche ; 3,3 V seulement, résistance série sur les LED, driver séparé pour les charges. Lignes 0/1 (EEPROM HAT) et 44/45/29/42/43 (noyau) réservées.
  • Fait relevé : HARDWARE.md:56-72 ; gpiodetect et gpioinfo relus le 22-11. Coût : code GPIO à réécrire et risque pour la carte.
