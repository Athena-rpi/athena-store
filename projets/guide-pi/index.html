Ce que vous obtenez

  • le guide en PDF — 36 pages, 14 chapitres en 4 parties, plus 3 annexes ;
  • la source Markdown (guide.md, 2 222 lignes), lisible partout, versionnée ;
  • deux vérificateurs : verifier_guide.py contrôle le guide contre les fichiers de la couche, verifier_pdf.py contrôle le PDF contre le Markdown ;
  • le script de mise en page (build_pdf.py) : le PDF se reconstruit depuis le Markdown, il ne se retouche pas à la main.

Aucun matériel n’est requis. Le guide s’installe sur un Pi qui tourne déjà, sous Debian 13 (trixie). Il ne parle ni de capteurs, ni de serre, ni d’achat.

Ce qu’il couvre

  • Partie I — la surveillance : les six grandeurs qui décident de presque tout (température, bridage, disque, unités en échec, horloge, Wi-Fi), les huit unités systemd et leur périodicité, le piège User= qui fait échouer un service « actif », la sonde SQLite et la page de statut sur 127.0.0.1.
  • Partie II — les données : le git bundle daté, vérifié avant d’être déclaré réussi, la restauration testée octet pour octet, le doctor hebdomadaire, la synchronisation et le .gitignore qui protège les secrets.
  • Partie III — aller plus loin : surveiller des paiements entrants sans intermédiaire, la validation quotidienne (sauvegarde, dépôt, modèle), le backlog et le cron qui exécute une tâche à la fois.
  • Partie IV — les pièges : dix pannes réelles avec leur commande de diagnostic (IPv6 non routable, i2c-dev absent, port déjà pris, pkill -f qui se tue soi-même, bus 1-Wire flottant, RPi.GPIO interdit sur Pi 5, numérotation BCM), puis une checklist de déploiement en 12 étapes.

Ce que la preuve montre

Chaque extrait du guide est copié d’un fichier qui existe sur le Pi d’origine, et chaque sortie de commande porte sa date de lecture. Le vérificateur le contrôle : 18 chemins cités existent, 50 blocs sont des copies littérales d’un fichier réel, 31 blocs de commandes n’appellent que des programmes présents sur la machine. Les fichiers absents sont déclarés absents, pas maquillés en exemples.

La page de preuve rejoue une commande réelle par chapitre (14), plus les deux vérificateurs, au moment où elle est construite : timers, User=, sonde de santé, curl sur la boucle locale, git bundle verify, restauration dans un dossier temporaire avec git fsck, doctor, surveillance des paiements, backlog, ports occupés, contrôle final. Si l’un de ces passages échoue, la page affiche l’erreur — elle n’affiche pas un chiffre inventé.

Aperçu du guide

Extrait gratuit : les trois premières pages du guide (titre, sommaire, début du chapitre 1). Le PDF complet fait 36 pages.

Les limites, dites avant l’achat

  • la sauvegarde décrite est non chiffrée : le bundle est lisible par quiconque obtient le fichier. Le chiffrement (age) n’est pas livré ;
  • tests/test_sauvegarde.py et sys/sauvegarde_chiffree.py n’existent pas : la restauration est documentée et exécutée à la main, pas automatisée ;
  • le dépôt distant est chez un tiers : « privé » n’est pas « chiffré » ;
  • sur la machine d’origine, le service web sert un code antérieur au fichier sur disque ; les six endpoints ont été vérifiés sur une instance éphémère du même fichier, et le redémarrage reste une action manuelle ;
  • athena-site-maintenance.* n’est pas copié dans state/units/ : une reconstruction à partir de ce seul dossier manque cette unité ;
  • les chiffres datés sont des instantanés : nombre d’échantillons, de bundles, de tâches. Ils changent à chaque passage.

Ces réglages visent une machine dédiée sous Debian 13, pas un poste de travail partagé. La copie « hors du Pi » reste à votre charge : le guide vous donne un artefact vérifiable, pas un hébergeur.
