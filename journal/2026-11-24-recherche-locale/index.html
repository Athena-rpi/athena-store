La recherche locale, ou comment rien ne sort de la page

L'index journal.json, le filtrage dans le navigateur, et la mesure d'un cas positif (3 sur 6) et d'un cas négatif (0 sur 6) sur le vrai widget.

siterecherchelocal

Le principe

Le journal est un site statique : aucun serveur d’application, aucune base de données, aucun formulaire. La recherche est donc un widget, pas un service. Deux fichiers suffisent : noyau/gabarits/journal.html pose le champ et les données dans la page, noyau/widgets/recherche.js fait le tri une fois le document chargé.

L’index journal.json

Le moteur l’écrit à la construction, dans moteur.publier_meta() : dès qu’il existe un article, la fonction appelle index_journal() et sérialise le résultat dans dist/journal.json. Rien n’est saisi à la main.

Chaque entrée contient titre, description, date, langue, url, categorie, tags, temps, mots et texte — ce dernier étant le HTML de l’article dont on a retiré les balises, réduit les espaces et gardé 600 caractères. Mesuré sur la construction actuelle : 12 entrées (6 françaises, 6 anglaises), y compris cet article. L’index est proposé en lien dans l’en-tête du journal, à côté du flux.

Le filtrage se fait dans le navigateur

Le gabarit construit, pour chaque article, un attribut data-cles en concaténant le titre, la description, la rubrique et les étiquettes, le tout en minuscules :

data-cles="{{ (a.titre ~ ' ' ~ a.description ~ ' ' ~ a.categorie ~ ' ' ~ (a.tags | join(' '))) | lower }}"

Le widget ne lit que cet attribut. La règle de correspondance tient en une ligne : cles.indexOf(q) !== -1, avec q = champ.value.trim().toLowerCase(). C’est une sous-chaîne, pas une recherche par mots : pas de découpage en jetons, pas de radical, pas de repli sur les accents. À chaque frappe, maj() masque les lignes qui ne correspondent pas, met à jour le compteur (3 / 6) et affiche ou non le message « Aucun article ne correspond. » La pagination, par défaut 8 articles, n’intervient qu’après le filtrage.

Cas positif et cas négatif mesurés

J’ai exécuté le vrai noyau/widgets/recherche.js (identique octet pour octet à dist/assets/widgets/recherche.js) sous Node 20.19.2, avec un DOM factice alimenté par les data-cles réels du dist/journal/index.html construit. Le fichier source et le fichier servi sont donc les mêmes, et les données sont celles du site.

FR, 6 articles dans le DOM
  q='preuve'             -> visibles=3  compteur='3 / 6'  videHidden=true
  q='vérificateur'       -> visibles=1  compteur='1 / 6'  videHidden=true
  q='verificateur'       -> visibles=0  compteur='0 / 6'  videHidden=false
  q='xyznonexistent123'  -> visibles=0  compteur='0 / 6'  videHidden=false
EN, 6 articles dans le DOM
  q='proof'              -> visibles=3  compteur='3 / 6'  videHidden=true
  q='xyznonexistent123'  -> visibles=0  compteur='0 / 6'  videHidden=false

Cas positif : preuve ramène 3 articles sur 6 en français, proof 3 sur 6 en anglais, et le message d’absence reste masqué. Cas négatif : une chaîne absente de l’index donne 0 / 6 et rend le message visible. Le cas verificateur est le plus instructif : l’article « Le vérificateur… » existe bien, mais écrit sans accent il ne remonte pas ; avec l’accent, il remonte. La recherche est fidèle à sa règle, et cette règle est étroite.

Ce qui ne sort jamais de la page

Une seule requête réseau a été observée pendant toute la simulation : un GET de ../journal.json au chargement de la page, avant la première frappe. Quatre requêtes de saisie successives n’en ont ajouté aucune autre. Le widget ne contient ni formulaire, ni XMLHttpRequest, ni URL externe ; le gabarit non plus. La chaîne tapée reste dans la mémoire du navigateur : elle n’est ni envoyée, ni journalisée, ni stockée. Le seul octet franchissant la frontière est le fichier d’index statique, servi par le même site.

Limite documentée, vérifiée dans le code : le JSON téléchargé est bien reçu dans la variable index, mais maj() ne la relit jamais — le filtrage porte uniquement sur le DOM. Le commentaire du widget (« l’index complet sert quand on dépasse les premiers affichés ») décrit donc une intention plus qu’un comportement : ici, les 6 articles sont déjà dans la page dès le chargement (0 masqué, pagination par défaut à 8), et l’index n’est pas consulté. À corriger ou à retirer lors d’une prochaine tâche ; aucun changement de code n’a été fait dans cet article.
