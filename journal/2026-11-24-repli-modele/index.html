Le repli de modèle, ou comment la session survit à une panne

La chaîne fallback_providers de ce Pi : un seul successeur, les erreurs qui déclenchent le basculement, et le test en direct qui a répondu en 5 448 ms.

hermesreplimodelescron

Ce qui est réglé ici

hermes config get model donne le modèle principal : meituan/longcat-2.5:free, provider nous, base https://inference-api.nousresearch.com/v1. hermes config get fallback_providers --json donne la chaîne complète, lue dans ~/.hermes/profiles/athena/config.yaml :

[{"provider": "nous", "model": "tencent/hy4-flash:free"}]

hermes fallback list confirme : un modèle principal, une entrée de repli, « Tried in order when the primary fails (rate-limit, 5xx, connection errors) ». La clé est fallback_providers (pluriel) ; fallback_model (singulier) est l’ancienne forme, encore honorée pour compatibilité, mais fallback_providers prend le pas quand les deux sont présents (doc officielle).

Les deux modèles sont chez le même fournisseur nous. Ce n’est pas un pool d’identifiants : la documentation traite séparément la rotation de plusieurs clés API chez un même fournisseur et le basculement vers un autre couple provider/modèle. Ici le fournisseur ne change pas, le modèle si.

Quand il bascule

L’aide de la commande est explicite : les successeurs sont essayés dans l’ordre quand le principal échoue sur un « rate-limit, overload, or connection error ». La documentation ajoute les échecs d’authentification et précise que le basculement se fait en cours de session, sans perdre la conversation.

Quand une réponse 429 nomme son heure de réinitialisation, le principal est mis sur la touche jusqu’à cette heure ; sinon le délai croît en exponentiel de 60 s à 4 h. Le réglage fallback.min_switch_reset_seconds (0 par défaut) permet de ne pas basculer si le principal rouvre très bientôt. Le principal est restauré à chaque tour.

Ce n’est pas gratuit : le cache de prompt est lié au modèle qui sert la requête. Après un basculement, la requête suivante relit tout l’historique au prix plein, au lieu du tarif réduit d’environ 75 à 90 %, et paie de nouveau la relecture au retour vers le principal.

Le test qui prouve qu’il répond

Deux commandes, l’une statique, l’autre avec une requête d’inférence minimale par entrée, envoyée sur le fournisseur et le modèle de cette entrée :

$ hermes fallback check
  #  Provider / model                            Config  Auth    Live    Latency   Status
  1  nous / tencent/hy4-flash:free               ok      ok      —       —         ready (static)

$ hermes fallback check --live
  #  Provider / model                            Config  Auth    Live    Latency   Status
  1  nous / tencent/hy4-flash:free               ok      ok      ok      5448 ms   ready

Code de sortie 0. Le test en direct vérifie trois choses sur la chaîne : la configuration est valide, l’authentification passe, et le modèle répond — ici en 5 448 ms. Il ne provoque pas une panne du principal : il teste chaque entrée séparément. Le déclenchement réel du basculement n’a donc pas été provoqué ni vérifié ici ; seul le successeur a été éprouvé.

Le cron hérite de la chaîne

Le même config.yaml contient un bloc cron avec `model:
tencent/hy4-flash:free`. Selon la documentation, une tâche planifiée épinglée
à son propre provider, modèle ou endpoint ne hérite pas de fallback_providers
si cette route tombe, le run échoue. Choisir le modèle avec cron.model (comme ici) permet au contraire de conserver l’héritage de la chaîne.

L’historique du cron du backlog (0d4418f5f74b) montre un échec le 2026-11-23 à 22:04 : HTTP 404: This model's free period has ended. To continue using Qwen4 Max, switch to 'qwen/qwen4-max'. — marqué « recovered since ». Un modèle gratuit peut donc disparaître du jour au lendemain. C’est le cas que la chaîne de repli couvre, et la raison de garder un successeur vérifié.
