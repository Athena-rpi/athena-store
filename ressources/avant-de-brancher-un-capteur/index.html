Avant de brancher un capteur

Cinq vérifications sur un Raspberry Pi 5 avant le premier câblage — tension, pull-up, librairie GPIO, ROMs fantômes 1-Wire et lecture d'une vraie sonde.

Sur cette page

  • 1. Le header est en 3,3 V, jamais en 5 V
  • 2. La résistance de pull-up
  • 3. lgpio contre RPi.GPIO
  • 4. Bus 1-Wire flottant : les ROMs fantômes de famille 0x00
  • 5. Lire une vraie ROM (famille 0x28, crc YES)
  • En résumé

Ce guide a été écrit sur le Pi 5 qui l’héberge. Toutes les commandes ci-dessous ont été exécutées le 22 novembre 2026 sur cette machine et les sorties reproduites sont celles obtenues. Quand quelque chose n’a pas pu être mesuré — tension, résistance, vraie sonde absente — c’est écrit explicitement.

1. Le header est en 3,3 V, jamais en 5 V

La machine est bien un Pi 5 à southbridge RP1 :

$ cat /proc/device-tree/model
Raspberry Pi 5 Model B Rev 1.1
$ gpiodetect
gpiochip0 [pinctrl-rp1] (54 lines)

La règle électrique est la suivante : logique 3,3 V sur le header, aucune entrée GPIO ne doit recevoir 5 V, résistance série sur chaque LED, alimentation séparée pour les relais et les charges. Elle est consignée dans le référentiel matériel de la machine, vérifié le 18 novembre 2026.

Le Pi 5 possède bien une broche 5 V (broche physique 2 et 4), mais c’est une alimentation, pas un niveau logique. Un capteur alimenté en 5 V dont la sortie revient directement sur une entrée GPIO doit passer par un convertisseur de niveau.

Non vérifié ici : aucune mesure de tension au multimètre n’a été faite — aucun instrument n’est branché. La recherche d’un nœud de lecture de tension dans l’arbre device-tree (find /proc/device-tree -iname '*voltage*' -o -iname '*regulator*') ne renvoie rien. La valeur 3,3 V est une règle matérielle documentée, pas une mesure relevée ce jour.

2. La résistance de pull-up

Sur un bus 1-Wire, la ligne de données doit être tirée vers 3,3 V par une résistance d’environ 4,7 kΩ. C’est la valeur prescrite par le référentiel matériel du Pi, vérifiée le 18 novembre 2026.

Le pilote w1-gpio est actif et demande le pull-up interne du GPIO :

$ cat /sys/bus/w1/devices/w1_bus_master1/w1_master_pullup
1
$ gpioinfo | grep onewire
        line   4: "GPIO4"   output drive=open-drain consumer="onewire@0"

w1_master_pullup à 1 signifie que le pilote utilise le pull-up interne du RP1. Ce pull-up interne ne remplace pas une résistance externe de 4,7 kΩ sur une ligne un peu longue : c’est la première cause de ROMs fantômes (section 4).

Non vérifié ici : la valeur de 4,7 kΩ n’a pas été mesurée à l’ohmmètre (aucun capteur, aucun composant branché).

3. lgpio contre RPi.GPIO

Sur le Pi 5, le header est géré par le RP1 (gpiochip0 [pinctrl-rp1]), pas par l’ancien contrôleur BCM2835. Le référentiel de cette machine prescrit lgpio ou gpiod, et non RPi.GPIO. Ce qui a été vérifié :

$ python3 -c "import lgpio; print(lgpio.__file__)"
/usr/lib/python3/dist-packages/lgpio.py
$ python3 -c "import importlib.metadata as m; print(m.version('lgpio'))"
0.2.2.0
$ python3 -c "import lgpio; h=lgpio.gpiochip_open(0); lgpio.gpio_claim_input(h,17); print(lgpio.gpio_read(h,17)); lgpio.gpiochip_close(h)"
0

RPi.GPIO est présent sur cette machine — il ne faut pas en déduire qu’il est utilisé. Version 0.7.2 (GPIO.VERSION), import réussi, et un test sans pilotage de sortie (broche 17 en entrée avec PUD_DOWN) répond :

$ python3 -c "import RPi.GPIO as G; G.setmode(G.BCM); G.setup(17,G.IN,pull_up_down=G.PUD_DOWN); print([G.input(17) for _ in range(5)]); G.cleanup()"
[0, 0, 0, 0, 0]

Sa source mentionne raspberrypi,rp1-gpio (ligne 503 de /usr/lib/python3/dist-packages/RPi/GPIO/__init__.py) : cette version reconnaît le RP1. La règle « pas de RPi.GPIO » est donc un choix de la couche logicielle de la machine, pas une panne observée ici. Un programme écrit avec lgpio reste cohérent avec le reste du système et expose directement les numéros BCM.

Numérotation : on utilise le BCM, pas le numéro de broche physique. La broche physique 7 est GPIO4, et c’est elle que le noyau a réservée à 1-Wire (consumer="onewire@0" ci-dessus). Les broches 27 et 28 (BCM 0 et 1) servent à l’EEPROM du HAT et ne se réutilisent pas.

4. Bus 1-Wire flottant : les ROMs fantômes de famille 0x00

Aucun capteur n’est branché sur cette machine. Le bus énumère pourtant des périphériques :

$ cat /sys/bus/w1/devices/w1_bus_master1/w1_master_slaves
00-8b8800000000
00-4b8800000000
$ cat /sys/bus/w1/devices/w1_bus_master1/w1_master_attempts
18545
$ sudo dmesg | grep -i "Family"
w1_master_driver w1_bus_master1: Family 0 for 00.538800000000.60 is not registered.
w1_master_driver w1_bus_master1: Family 0 for 00.d38800000000.ec is not registered.

Une lecture immédiatement après en donne d’autres (00-4b8800000000, 00-8b8800000000, 00-cb8800000000), puis encore d’autres (00-cb8800000000, 00-2b8800000000, 00-ab8800000000) : les ROMs changent à chaque recherche. Le préfixe 00- est une famille invalide — le noyau le dit lui-même : « Family 0 … is not registered ». Ce ne sont pas des sondes et il n’existe pas de fichier w1_slave correspondant :

$ ls /sys/bus/w1/devices/00-4b8800000000/
ls: cannot access '/sys/bus/w1/devices/00-4b8800000000/': No such file or directory

Un vrai DS18B20, lui, annonce une ROM de famille 0x28 (28-…) et reste stable d’une recherche à l’autre. Le fait que la ligne soit tour à tour pilotée en sortie et lue en entrée explique que gpioinfo la montre en output drive=open-drain alors que pinctrl get 4 peut afficher 4: ip pn | lo // GPIO4 = input : ce sont deux instants différents du même cycle 1-Wire.

5. Lire une vraie ROM (famille 0x28, crc YES)

Quand un DS18B20 est branché avec son pull-up, la procédure est :

$ cat /sys/bus/w1/devices/w1_bus_master1/w1_master_slaves
28-0123456789ab        <- famille 0x28, stable
$ cat /sys/bus/w1/devices/28-0123456789ab/w1_slave
6e 01 4b 46 7f ff 0c 10 57 : crc=57 YES
6e 01 4b 46 7f ff 0c 10 57 t=22187

La première ligne se termine par crc=… YES : le contrôle de redondance de la ROM est bon, la température de la deuxième ligne est en millidegrés Celsius. Pour distinguer automatiquement le vrai du fantôme, ce script a été exécuté sur le bus actuel :

ROM=$(cat /sys/bus/w1/devices/w1_bus_master1/w1_master_slaves)
for r in $ROM; do
  case "$r" in
    28-*) echo "Vrai DS18B20 : $r"; cat /sys/bus/w1/devices/$r/w1_slave;;
    00-*) echo "ROM fantome (famille 0x00) : $r - ignorer";;
    *) echo "Famille inconnue : $r";;
  esac
done

Sortie réellement obtenue :

ROM fantome (famille 0x00) : 00-cb8800000000 - ignorer
ROM fantome (famille 0x00) : 00-2b8800000000 - ignorer
ROM fantome (famille 0x00) : 00-ab8800000000 - ignorer

Non vérifié ici : aucun capteur de famille 0x28 n’est branché — la listing ne contient que des 00-* et w1_bus_master1. La ligne crc=… YES n’a donc pas été observée sur cette machine ; la procédure est donnée pour le jour où une sonde est connectée.

En résumé

  1. 3,3 V sur le header, jamais 5 V sur une entrée GPIO.
  2. Pull-up 4,7 kΩ vers 3,3 V pour le bus 1-Wire.
  3. lgpio ou gpiod, numéros BCM ; RPi.GPIO présent mais non utilisé par la couche.
  4. Une ROM 00-… changeante est un fantôme, pas une sonde.
  5. Une vraie sonde donne une ROM 28-… stable et crc=… YES dans w1_slave.
