Format du manifeste de preuve, champ par champ

Référence du format preuve.yml — six sections, rôle de chaque champ, erreurs rejetées et pourquoi, exemples de preuves honnêtes et malhonnêtes.

Cette page est la référence du format de manifeste utilisé par le kit « Page de preuve ». Elle décrit le comportement réel du moteur (store/noyau/preuves.py), lu et rejoué le 22 novembre 2026 sur ce Pi. Elle complète l’article Le manifeste de preuve, ligne à ligne (journal du 20-11-2026), qui prenait un projet concret ; ici c’est le format qui est décrit, indépendamment du projet.

→ Voir aussi l’arsenal de vérification : les commandes réellement exécutées sur le Pi, ce que chacune vérifie et le piège qu’elle évite.

1. Emplacement et liaison au projet

Un manifeste est un fichier YAML nommé preuve.yml déposé dans store/projets/<slug>/preuve.yml. C’est le chemin qui lie le manifeste au projet, pas la clé projet: : le moteur ne lit jamais cette clé. Elle est déclarative, pour l’humain qui lit le fichier.

projet: kit-preuve      # déclaratif — non lu par le moteur
commandes: …

Un projet sans manifeste est signalé par contrôle() comme <slug> : manifeste absent (…/preuve.yml) et la construction échoue.

2. Les six sections

Section Nature Lu par collecter() Vérifié par contrôle()
tests liste de {fichier, commande} oui existence du fichier
commandes liste de {titre, commande} oui —
compteurs liste de {titre, base, sql} oui existence de la base
fichiers liste de chemins oui existence de chaque chemin
captures liste de {image, titre} ou de chemins oui existence de l’image
limites liste de textes libres oui (aplaties) —

Une section absente vaut liste vide. commandes et limites sont les seules sections dont contrôle() ne vérifie rien : une commande qui échoue est une preuve d’échec, pas une erreur de construction.

3. Champ par champ

tests — fichier, commande

tests:
  - fichier: tests/test_verifier_site.py
    commande: python3 -m unittest tests.test_verifier_site -q
  • fichier : source contenant des définitions def test_…. Le nombre de tests affiché est compté par une regex sur ce source (r"^\s*def (test_\w+)", drapeau multiligne), pas lu dans la sortie de la commande. Fichier absent → compte 0, et contrôle() rejette le manifeste.
  • commande : shell exécutée avec shell=True, depuis la racine de la couche, délai maximal 60 s. Le verdict (OK / échec) vient du code de retour, pas du nombre de tests. Supprimer un def test_ fait baisser le chiffre même si la commande réussit encore.

Le nombre et le verdict sont donc deux mesures distinctes : l’une vient du fichier, l’autre de l’exécution.

commandes — titre, commande

commandes:
  - titre: Système et architecture, relus sur la machine
    commande: uname -srm
  • titre : libellé libre affiché en page ; absent, le moteur affiche la commande elle-même.
  • commande : cf. exécution ci-dessous. Stdout et stderr sont concaténés ; si la sortie est vide, la page affiche (aucune sortie).

Règle d’écriture (non garantie par le moteur) : les commandes tournent avec les droits de celui qui construit le site et doivent rester en lecture seule.

compteurs — titre, base, sql

compteurs:
  - titre: Relevés de santé enregistrés sur le Pi
    base: data/health.db
    sql: select count(*) from samples
  • base : fichier SQLite. Un chemin absolu (/…) est ouvert tel quel ; sinon il passe par la résolution décrite plus bas. La connexion se fait en URI file:…?mode=ro : lecture seule, le manifeste ne peut pas écrire dans la base qu’il mesure.
  • sql : requête exécutée ; la première ligne du résultat est affichée, ses colonnes jointes par un espace. Une requête invalide ou une base absente produit une erreur affichée (collecter() ne lève jamais) ; une base absente est en plus rejetée par contrôle().

fichiers — liste de chemins

fichiers:
  - store/noyau/preuves.py
  - store/projets/kit-preuve/README.md

Pour chaque chemin, le moteur affiche la taille en octets et les 12 premiers caractères hexadécimaux du SHA-256 du fichier. Un fichier livré qui change d’empreinte se voit. Un chemin absent est marqué absent dans la page et rejeté par contrôle().

captures — image, titre

captures:
  - image: ressources/extrait-kit-page-1.png
    titre: "Exemple de rendu : extrait figé d'une page du guide"

Deux formes acceptées : {image, titre}, ou un simple chemin en texte (- ressources/image.png, titre vide). L’image doit exister, sinon contrôle() rejette. Mettre des guillemets au titre s’il contient un deux-points, sinon YAML le lit comme une structure.

limites — texte libre

limites:
  - "Cette page ne prouve aucune qualité métier."
  - "Le compteur est un instantané, pas une garantie."

Bloc rendu en bas de page. Piège réel : une limite contenant : non citée est lue par YAML comme un dictionnaire ; le moteur la remet à plat (_aplatir_limite) en clé : valeur — clé : valeur plutôt que d’afficher du JSON. Citez vos limites.

Résolution des chemins et exécution

  • ressources/… et assets/… sont résolus depuis store/ ; tous les autres chemins depuis la racine de la couche (~/Documents/Athena).
  • Chaque commande tourne avec cwd = racine de la couche, timeout=60 s, shell=True. Sortie tronquée à ses 12 dernières lignes et 1 200 derniers caractères : un long journal peut masquer son début.
  • Verdict : 0 = OK ; sinon code de retour N ; dépassement → timeout après 60 s ; erreur système → message Python. La date affichée (« recalculé le ») est date.today(), jamais une date écrite à la main.

4. Erreurs rejetées, et pourquoi

contrôle('<slug>') est joué avant la construction par store/outils/site.py. Chaque entrée devient une erreur et la construction s’arrête :

Erreur renvoyée Cause Pourquoi c’est rejeté
<slug> : manifeste absent (…) pas de preuve.yml une page de preuve sans source de preuve n’a pas de sens
test introuvable : <fichier> fichier de tests inexistant le nombre de tests serait un 0 silencieux, pas une mesure
fichier introuvable : <chemin> chemin de fichiers inexistant annoncer un fichier livré qui n’existe pas ment sur le contenu
capture introuvable : <image> image de captures inexistante la galerie afficherait une image cassée
base introuvable : <base> base de compteurs inexistante le compteur ne peut pas être rejoué par un lecteur

Ces cinq messages ont été relevés tels quels en rejouant contrôle() sur un manifeste temporaire contenant ces cinq défauts (22-11-2026). À l’inverse, une commande en échec, un timeout, une requête SQL invalide ou une base absente dans collecter() ne sont pas rejetés : l’erreur est publiée dans la page. C’est la distinction centrale : on refuse ce qui ne peut pas être mesuré, on affiche ce qui a été mesuré et qui a échoué.

Au-delà du moteur, site.py check (store/noyau/verifier.py) rejette aussi une traduction manquante, un lien interne cassé, une page orpheline et un jeton de donnée réelle non remplacé.

5. Preuves honnêtes et malhonnêtes

Honnête : mesurer, montrer l’échec, dire la limite

commandes:
  - titre: Bus I2C et SPI
    commande: ls /dev/i2c-* /dev/spidev* 2>/dev/null
limites:
  - "Le bus I2C n'a pas de module i2c-dev chargé : aucun périphérique."

Ici la commande sort en code de retour 2 parce que /dev/i2c-1 n’existe pas ; le moteur affiche ce code, et la limite dit ce que la preuve ne montre pas. Le lecteur voit à la fois la mesure et son absence de portée. C’est le contrat du kit.

Malhonnête : écrire le chiffre au lieu de le mesurer

commandes:
  - titre: Nombre de tests
    commande: echo "12 tests OK"        # MAUVAIS : le chiffre est écrit à la main

La page affichera 12 tests OK, mais rien n’a été exécuté ni compté. Le chiffre est une affirmation, pas une preuve. Le manifeste doit déléguer le chiffre à une commande ou à un compteur SQL.

Malhonnête : masquer l’échec

commandes:
  - titre: Bus I2C
    commande: ls /dev/i2c-* 2>/dev/null || true   # MAUVAIS : || true force le code 0

|| true transforme un échec en succès : le verdict « OK » affiché ne veut plus rien dire. Même effet avec une redirection qui cache stderr alors que la commande échoue, ou un exit 0 forcé. Une preuve honnête laisse le code de retour réel apparaître.

Malhonnête : sélection biaisée et limites absentes

Un manifeste qui ne mesure que ce qui arrange — en omettant les tests qui échouent, les fichiers manquants ou la section limites — reste techniquement valide pour contrôle(). Le moteur ne peut pas juger l’honnêteté du choix des mesures : c’est pour cela que le manifeste est public dans le dépôt et que la section limites est attendue. Un lecteur doit pouvoir lire ce qui est mesuré et ce qui ne l’est pas.

6. Ce que le format ne garantit pas

  • Que les mesures choisies soient représentatives : c’est un choix humain, visible dans le manifeste public.
  • Que les commandes soient inoffensives : c’est une règle d’écriture, pas une garde du moteur.
  • Que le début d’une longue sortie soit visible : troncature à 12 lignes / 1 200 caractères.
  • Que les tests du moteur lui-même existent : la confiance repose aujourd’hui sur la relecture du code et sur les exemples rejoués (tâche T89 du backlog).
