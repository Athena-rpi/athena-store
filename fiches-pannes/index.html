Fiche 1 — Quota gratuit saturé (HTTP 429)

  • Cause : le modèle épinglé pour les cron (qwen/qwen4-max:free) est en « fair-share » ; le routeur répond retry after 122 s. Un redémarrage ne répare rien : le modèle répond, mais le quota est plein.
  • Symptôme : le planificateur tourne, les jobs sont actifs et programmés, mais les exécutions échouent les unes après les autres. Ce n’est pas un cron cassé ; c’est un quota épuisé.
  • Commande de diagnostic : grep -n '429' data/gardien_message.txt — chercher « fair-share 429 » et le délai de reprise, puis comparer avec la réponse du modèle lui-même.
  • Correctif : attendre la libération du quota ou épingler un autre modèle gratuit ; prévoir un recul/réessai (backoff) plutôt qu’un redémarrage. Le repli tencent/hy4-flash:free est vérifié comme opérationnel.
  • Constaté sur ce Pi : rejoué le 24-11, data/gardien_message.txt:5 porte « fair-share 429 — le routeur répond « retry after 122 s » » et :3 relate « le backlog 1 … venait d’échouer 8 fois de suite ». Le même fichier note qu’un redémarrage n’avait rien réparé, le modèle ayant répondu à la vérification. Coût : cron paralysé jusqu’à la relance (temps, pas d’argent).

Fiche 2 — Exécution de cron figée

  • Cause : un run reste ouvert (finished_at à NULL) et continue de progresser ; la file derrière lui s’immobilise. Le gardien utilisait un seuil de 0 minute, donc sa durée journalisée ne mesurait pas la durée réelle.
  • Symptôme : « annulé … figé depuis 0 min (seuil 0 min) » dans le journal du gardien ; aucun job suivant ne démarre, ce qui ressemble à de l’inactivité alors que la file est bloquée.
  • Commande de diagnostic : grep -n 'annulé' logs/gardien.log — relever les horodatages d’annulation et le seuil affiché.
  • Correctif : sys/gardien.py (timer de 15 min) annule et relance au-delà de 90 min (GARDIEN_SEUIL_S) ; le run interrompu reste dans la file et repart au passage suivant, rien n’est perdu.
  • Constaté sur ce Pi : rejoué le 24-11, logs/gardien.log:2 et :8 donnent deux annulations le 2026-11-21 à 13:07:58 et 13:08:01 EST, toutes deux « figé depuis 0 min (seuil 0 min) » (jobs 0d4418f5… et 678637b0…). data/gardien_message.txt:3 rapporte un run du backlog 2 ouvert depuis 19h43, soit 2 h 28 perdues. Coût : 2 h 28 de file bloquée.

Fiche 3 — Grand livre : scan long et non incrémental

  • Cause : le scan n’est pas incrémental ; il est plafonné à 200 000 blocs. L’état est écrit à latest même quand le scan est tronqué, donc un transfert hors fenêtre peut être manqué.
  • Symptôme : le cron 08:50 met ~20 min ; les lancements manuels de 09:00 dépassent 60 s puis 300 s.
  • Commande de diagnostic : grep -n -i 'scan\|RPC\|blocs\|ledger' data/daily_report.txt data/auto_analyse.txt data/weekly_report.txt — ne pas utiliser un numéro de ligne fixe : le rapport quotidien est régénéré chaque jour et ses lignes tournent (le 24-11, la ligne 4 est une mesure de santé, pas le ledger).
  • Correctif : reprendre depuis data/ledger_state.json et ne pas avancer latest tant que le scan est plafonné ; relancer ensuite wallet/ledger.py. Le passage du 22-11 à 09:10 était sorti en exit 0 avec 0 transfert.
  • Constaté sur ce Pi : le 24-11, data/daily_report.txt:2 relève ledger.py exit 0, BTC 0 tx, USDC/Base 0, USDC/Ethereum 17,28, « Blocs scrutés : Base 61 695 661 / ETH 26 485 536, 0 transfert » (08:50:32), et :3 signale le passage 08:50 encore actif à 09:00 (rattrapage). L’incident historique est trace de façon durable dans data/auto_analyse.txt:29,38 (« scan plafonné à 200 000 blocs, ~2 000 appels RPC », ~20 min) et data/weekly_report.txt:23 (état latest avancé malgré le plafond). Coût : ~20 min/jour et risque de transfert manqué.

Fiche 4 — Poussées git en échec

  • Cause : réseau ou clé SSH indisponible au moment du cron de sauvegarde.
  • Symptôme : « ÉCHEC de poussée (réseau ou clé SSH) » dans le journal ; le commit reste local, la couche privée n’est pas à jour sur le dépôt.
  • Commande de diagnostic : grep -n 'ÉCHEC de poussée' logs/git_sync.log | tail.
  • Correctif : rétablir le réseau/la clé puis rejouer bash sys/git_sync.sh ; le script relit @{u}..HEAD pour pousser un commit même déjà présent localement.
  • Constaté sur ce Pi : rejoué le 24-11, logs/git_sync.log:141 porte [2026-11-22T03:45:56-05:00] ÉCHEC de poussée et :148 [2026-11-22T06:17:25-05:00] — deux échecs en moins de 2 h 30. Coût : couche privée non sauvegardée pendant l’incident (risque, pas d’argent).

Fiche 5 — IPv6 cassé

  • Cause : la résolution dual-stack attend le repli IPv4 avant de se connecter.
  • Symptôme : toute requête réseau bloque ~24 s, puis aboutit en IPv4.
  • Commande de diagnostic : grep -n 'precedence ::ffff:0:0/96' /etc/gai.conf /etc/gai.conf.bak-20261118 — comparer la ligne active du fichier courant avec la ligne commentée de la sauvegarde.
  • Correctif : precedence ::ffff:0:0/96 100 dans /etc/gai.conf (sauvegarde .bak-20261118) → IPv4 en premier, ~0,02 s. En dépannage : curl -4 ou getaddrinfo filtré sur AF_INET.
  • Constaté sur ce Pi : rejoué le 24-11, la ligne 66 de /etc/gai.conf est active (precedence ::ffff:0:0/96 100) tandis que les lignes 50 et 54 le sont commentées dans /etc/gai.conf.bak-20261118. Le gain mesuré avant correction est relaté dans HARDWARE.md:102-106. Coût : ~24 s par requête avant correction (temps).

Fiche 6 — Bus 1-Wire flottant, ROMs fantômes

  • Cause : aucune sonde branchée et aucune résistance de pull-up vers 3V3 ; le bus énumère des devices invalides dont l’identifiant change à chaque recherche.
  • Symptôme : des entrées 00-… apparaissent dans /sys/bus/w1/devices/ ; w1_master_attempts grimpe ; le noyau journalise « Family 0 … is not registered ».
  • Commande de diagnostic : ls /sys/bus/w1/devices/ — relever deux fois de suite : si l’identifiant change, ce n’est pas une sonde.
  • Correctif : résistance de 4,7 kΩ vers 3V3 sur GPIO4 (+ masse) et un vrai DS18B20 (famille 0x28). Tant qu’il n’y a que des 00-*, aucune température n’est valide. Aucun achat de matériel n’est fait : projet gelé par Jacob.
  • Constaté sur ce Pi : le 24-11, ls /sys/bus/w1/devices/ renvoie 00-034400000000, 00-fd4400000000, w1_bus_master1 — identifiants différents de ceux relevés le 22-11 dans la FAQ (00-436800000000, 00-836800000000), ce qui confirme qu’ils sont fantômes. HARDWARE.md:50-54,144-147 décrit le bus flottant et le pull-up requis. Coût : fausses mesures et temps de diagnostic perdu.

Fiche 7 — /dev/i2c-1 absent au boot

  • Cause : dtparam=i2c_arm=on active le nœud RP1 (i2c@74000, GPIO2/3) mais le module i2c-dev n’est pas chargé au démarrage.
  • Symptôme : aucun /dev/i2c-* n’existe ; i2cdetect échoue, alors même que le nœud matériel est okay.
  • Commande de diagnostic : ls /dev/i2c-* 2>&1; lsmod | grep i2c_dev — le premier échoue, le second ne renvoie rien.
  • Correctif : charger le module de façon persistante avec echo i2c-dev | sudo tee /etc/modules-load.d/i2c-dev.conf (à faire à la main, hors cron). Piège : i2c-13/i2c-14, quand ils existent, sont le DDC HDMI — pas le header.
  • Constaté sur ce Pi : rejoué le 24-11, ls /dev/i2c-* répond « No such file or directory » et lsmod | grep i2c_dev ne renvoie rien, alors que HARDWARE.md:44-47 rapporte un modprobe i2c-dev manuel vers 15:55 le 22-11 — le module est donc bien perdu à chaque reboot. Coût : bus I2C indisponible après chaque redémarrage (temps de diagnostic).

Fiche 8 — Inférence « GPU » seize fois plus lente

  • Cause : le delegate WebGPU (Dawn/Vulkan) exige shaderUniformBufferArrayDynamicIndexing et shaderSampledImageArrayDynamicIndexing, que le pilote v3dv (mesa 26.2.2, V3D 7.1.10.2) n’expose pas (= 0). Dawn rejette V3D et retombe sur llvmpipe (logiciel).
  • Symptôme : 278,7 ms au lieu de 16,8 ms en CPU 4 threads (16,6× plus lent) ; pire, CompiledModel(ptr, env) affiche un « GPU OK » alors qu’il ne charge aucun modèle.
  • Commande de diagnostic : python3 litert/probe_vulkan.py (features V3D à 0) ; comparer avec CompiledModel.from_file(...) et les mesures de data/litert_etat.txt.
  • Correctif : rester en CPU XNNPACK 4 threads ; ne jamais valider un modèle avec le simple constructeur. Pas de NPU sur Pi 5 (plugin Qualcomm inutilisable, libQnnSystem.so absent).
  • Constaté sur ce Pi : le 24-11, litert/probe_vulkan.py est relu (2 514 octets) et data/litert_etat.txt:20-26 donne 16,80 ms à 4 threads, :44,58 donnent 278,7 ms en « GPU » et le bilan « 16,6× plus lent », :48 identifie llvmpipe (LLVM 19.1.7), :51-55 les deux features à 0. HARDWARE.md:177-189 consigne la loi matérielle. Coût : ×16 sur l’inférence et fausse validation.

Fiche 9 — Page de statut 8081, panneau Backlog en erreur

  • Cause : deux bugs dans health_web.py — backlog.charger() appelé sans son argument fichier, et une référence à backlog.JOURNAL, attribut inexistant (le journal est state/backlog/journal.md).
  • Symptôme : la page d’accueil locale ne peut pas afficher les prochains actes ; le panneau Backlog part en erreur.
  • Commande de diagnostic : curl -s --max-time 6 -4 http://127.0.0.1:8081/ | grep -i backlog, puis python3 tests/verifier_accueil.py (12 contrôles).
  • Correctif : passer le chemin du fichier à charger() et lire state/backlog/journal.md ; vérifier avec verifier_accueil.py.
  • Constaté sur ce Pi : le 24-11, le curl local répond (code 0) et le HTML contient bien les marqueurs backlog, /api/backlog et backlog/taches.json · tâches prêtes dont les dépendances sont faites. HARDWARE.md:294-298 relate les deux bugs corrigés et le journal backlog T04 la remise en service. Coût : page de surveillance inutilisable jusqu’au correctif.

Fiche 10 — RPi.GPIO et numérotation sur RP1

  • Cause : le header est piloté par la southbridge RP1 (gpiochip0) ; RPi.GPIO ne le pilote pas correctement, et la numérotation physique n’est pas la numérotation BCM.
  • Symptôme : import ou appel GPIO défaillant, broches qui ne répondent pas, ou mauvais GPIO ciblé. Risque matériel si 5 V est appliqué au header (logique 3,3 V).
  • Commande de diagnostic : gpiodetect; gpioinfo | grep onewire — vérifier le contrôleur et la ligne, jamais le numéro de broche.
  • Correctif : utiliser lgpio ou gpiod/libgpiod, raisonner en BCM vérifié par gpioinfo, jamais en numéro de broche ; 3,3 V seulement, résistance série sur les LED, driver séparé pour les charges. Lignes 0/1 (EEPROM HAT) et 44/45/29/42/43 (noyau) réservées.
  • Constaté sur ce Pi : rejoué le 24-11, gpiodetect donne gpiochip0 [pinctrl-rp1] (54 lines) (plus les gpiochip 10 à 13 du SoC) et gpioinfo donne line 4: "GPIO4" output drive=open-drain consumer="onewire@0". HARDWARE.md:56-72 consigne les lignes réservées et la règle 3,3 V. Coût : code GPIO à réécrire et risque pour la carte.
